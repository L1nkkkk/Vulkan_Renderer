# 角色资料索引

这些文件供 agent 在对应角色下使用。现在只准备资料，不开始 review、口试或注入。所有行为仍受 [AGENTS.md](../AGENTS.md) 和当前 Task 的分工约束。

| 入口 | 读取资料 | 产出 |
|---|---|---|
| `/review <文件>` | [review-checklist.md](review-checklist.md) | 带位置、影响与依据的问题清单，不改代码 |
| `/exam 01`～`/exam 07` | 对应 `oral-exam-XX.md` | 逐题口试，最后保存真实结果 |
| `/sabotage 01`、`/sabotage 03` | 对应 `saboteur-XX.md` | 注入一个清单内的问题，等待用户独立定位 |

学习者从 [tasks/](../tasks/README.md) 查看计划，从 [README](../README.md) 查看公开口试题。为保留练习效果，口试前避免阅读评分细则，排错前避免打开注入清单或 `.sabotage-active`。

## 口试执行规则

1. 先读 AGENTS.md、当前 Task、对应题库和已有口试记录。00 无口试，不创建 `oral-exam-00.md`。
2. 确认前置 Task 已验收；当前 Task 的功能、学习文档及指定排错练习已完成，再开始口试。
3. 一次只问一题，等待用户回答。最多一次澄清追问，只请其澄清原意，不提供概念、关键词或答案提示。
4. 题库“通过标准”的各项都需满足，合理的等价表达可通过；不能因术语一致就忽略错误因果。具体代码题必须结合用户实际实现。
5. 明确区分“规范保证”“某设备上的观察”和“自己的设计选择”；不将特定教程写法当作 Vulkan 的唯一合法实现。
6. 当题库涉及 API 或第三方源码版本差异时，核对用户实际版本和题后官方资料；用户有充分证据指出题目前提错误，应修正评分依据。
7. 全部问题回答完后，逐题报告通过 / 未通过、一句话评语和未通过题目的阅读材料；写入 `docs/oral/taskXX.md`，格式严格按 AGENTS.md。
8. M/M 才为通过，否则记录未通过（N/M），不允许打完成 tag。补考只问尚未通过的题。
9. 补考在原记录后追加本次日期、实际问题与结果，保留历史；汇总结果合并既往通过题和本次新通过题，不将复用的成绩伪装成新回答。

评分标准是考官检查维度，不是向用户提供的作业答案；考试过程中不展示整份标准。

## 故障注入执行规则

1. 只在用户发出 `/sabotage 01` 或 `/sabotage 03` 后启动；已有 `.sabotage-active` 时先完成原练习，不叠加故障。
2. 确认当前实现稳定且前置验收成立，再确认工作区干净，或按 AGENTS.md 保存工作区。若使用 stash，记录精确引用和原工作区状态，恢复时不覆盖后续修改。
3. 从当前 Task 清单选择满足适用条件的一项，只改一个代码位置。不得扩大成多个根因，不得用构建错误替代同步 / barrier 练习。
4. `.sabotage-active` 记录 Task、注入编号、目标路径和位置、基线提交、实际改动以及必要的 stash 引用；该文件已被 Git 忽略。不要在聊天或提交说明中透露内容，不提交故障。
5. 核对改动范围和可构建性；注入后的对外回复严格为“已注入，开始排查”，不暴露文件、候选项、症状或验证输出。
6. 用户说“找到了”并说明根因后，对照本次记录判定。正确时删除 `.sabotage-active` 并回复“正确”；错误时只回复“不是这个”。由用户修复并验证正常路径，不悄悄替用户修复。
7. 用户说“放弃”时按 AGENTS.md 公布答案并追加真实排错记录，标注“由 agent 解决”；不编造排查路径或耗时。恢复基线改动时只处理本次注入，核对后结束练习。
8. 如果预设故障不适用于当前实现，明确说明未注入；不能声称已注入，也不能越过清单临时设计故障。修订题库属于另一个明确的规划动作。
