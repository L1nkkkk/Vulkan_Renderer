## 每个任务怎么推进

1. 确认前置验收、当前 Task 编号和角色，阅读该 Task 的分工表。
2. 用户先写需要独立完成的接口、判断或方案，再提出具体的生成或 review 请求。
3. 按检查表逐步实现，每次只验证当前新增的行为；失败时记录现象、预期与自己的判断。
4. 用户完成学习文档。agent 只能按规则事后校对事实，不补写论证、观点或答案。
5. 完成功能、工具验证和该 Task 指定的排错练习，再进行口试。00 无口试。
6. 用户提交自己的代码与文档；agent 生成代码单独提交并使用 `[agent]` 前缀，前提是用户已完成逐行注释。
7. 验收通过后同步更新本目录检查项、README 状态与当前 Task；按用户指令合并、打 tag，然后进入下一项。

建议工作分支名写在各检查表中，只在开始该 Task 时建立。任务尚未通过时保持未完成，不用分支存在、提交次数或画面能跑代替验收。

## 证据与记录

- 功能证据：实际运行行为、相关代码位置、必要的截图或工具观察；不凭计划预填结果。
- 调试证据：Validation 设置与输出、RenderDoc 事件或资源位置、必要时的 Nsight 对照。捕获文件默认不入 Git，文档记录本地位置和复现条件。
- 文档证据：用户在 `docs/` 中写出的对应 Task 文档；不会先生成带答案的模板。
- 口试证据：考官在 `docs/oral/taskXX.md` 中写入每题结果、评语和待补阅读；仅完整考试或补考后记录实际结论。
- 排错记录：卡住超过 30 分钟时按 AGENTS.md 记录到 `docs/debug-log.md`。未发生的排错不造记录。

每完成两个 Task 回顾排错记录。按顺序在 01、03、05、07 结束时统计这两个 Task 中 `解决者：agent` 的条数 / 有明确解决者的总条数；没有记录时注明“无样本”，不算成 0%。超过 40% 时提醒收紧下一 Task 的生成范围。
